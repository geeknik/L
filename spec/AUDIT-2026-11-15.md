# Project audit and implementation record — 2026-11-15

## Scope and conclusion

Reviewed the design/calculus, Python and Rust language/gate paths, proxy ingress,
CLI, differential oracle, conformance/exploit/benchmark runners, dependencies and
release instructions. The earlier project had substantially drifted: structural
acceptance was described as a security monitor without trusted capability state,
authenticated endorsements or input influence enforcement.

The operator selected the full security gate and an in-house authority. The work
now separates structural scanning from actual authorization and implements the
signed runtime contract in both languages. This is progress toward 1.0, not a
release verdict. See MILESTONE.md for still-open deployment/design obligations.

## Issues caught while implementing authority

- The initial Python verifier accepted a forged identity-point Ed25519 signature
  under a weak configured public key. Independent reproduction led to replacing
  that backend with PyNaCl/libsodium point validation. Both languages now require
  canonical prime-order public keys and signature R points; normal and malformed
  key controls are tested. No custom signature arithmetic was introduced.
- Python accepted lone-surrogate signed strings that Rust rejected. Signed schema
  validation now requires Unicode scalar strings in both implementations.
- A full nonce store could prevent a valid revocation while grants stayed usable.
  Capacity refusal now latches the session closed to privileged execution and
  authority updates. Replay records are never silently evicted.
- Host review identified that tool outputs need trusted confidentiality and tool
  provenance, not just the caller's input label. The local-host contract requires
  conservative output labels and recipient checks before dispatch.
- Cross-thread callback reentry could deadlock the host serialization lock. Host
  operations now refuse concurrent entry instead of waiting, with a regression
  exercising the callback/thread interaction.

## Verification boundaries

`uv run --locked python scripts/verify.py` is the repeatable local verification
entry point. Tests include signed interoperability in both directions, adversarial
authority cases and structural differential fuzzing. Runtime dependency advisory
checks were clean on this date; they must be repeated for release. Hosted CI has
not been run or published by this work.

Final local run exited zero: 273 Python tests (ResourceWarnings as errors),
75 structural Rust tests plus 12 security tests, strict mypy on all 12 runtime
source files, all-target Clippy with warnings denied, 10 conformance tests,
structural exploit contracts, local signed-host demo, 500 differential cases
plus 9 replay fixtures, generated-limits check and 5 synthetic positive controls.
The host-specific suite has 14 tests. Both Python-issued and freshly Rust-issued
signatures exercise the other implementation.

Files changed span `lang/`, `gate/` (new authority/security/host), `rust/src/`
(new authority/security/limits), `proxy/`, `cli/`, `conformance/`, `tests/`,
`rust/tests/`, `rust/examples/`, `demos/`, `benchmarks/`, `scripts/`, `spec/`,
dependency manifests/locks, `.github/workflows/verify.yml`, README, CALCULUS,
DESIGN and local AGENTS. The checkout still has no tracked files or commits;
`git diff --check` alone therefore cannot verify these untracked edits.

The local reference host tests real callback side effects, not a deployed MCP
host or real model utility. It starts fresh unresumable subjects after restart;
the underlying SecurityGate state is still in-memory. Authority key custody and
rotation, resumable-session persistence, canonical L binary projection, a frozen
real-agent utility experiment, licensing and release review remain open. No
mechanized proof or universal absence of vulnerabilities is claimed.
